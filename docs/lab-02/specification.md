# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Enable a Requester to create IT support tickets with attachments, view and search 
their own tickets in My Tickets, and inspect ticket details — all under a temporary 
Development Requester identity that simulates per-user ownership ahead of real 
authentication in Lab 3.

## 2. Stakeholder Request Interpretation
The IT department needs a Requester-facing ticketing experience where a user can 
describe a problem, categorize it, attach evidence, and submit it for a unique 
Ticket Number. Since real login isn't ready yet, a temporary "Development Requester" 
selector simulates being logged in as one of several seeded test users, and the 
system must strictly prevent one Requester from seeing another's tickets.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism only)
- Create Ticket (form, validation, attachments, submission)
- My Tickets (list, search, filter, sort, pagination)
- Requester Ticket Detail (read-only view + attachment management)
- Attachment lifecycle: upload, download, soft-remove
- Ownership enforcement (backend + frontend)

### Excluded
- Authentication, login, passwords, sessions, tokens
- IT Staff dashboard, ticket assignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Status changes beyond initial "New" (no resolve/close/reopen)
- Administrator functions (user/category/related-system management)

## 4. Functional Requirements

- FR-01 A Requester can create a new Ticket by submitting category, related system, 
  summary, description, requested priority, and optional attachments.
- FR-02 The system generates a unique, backend-assigned Ticket Number upon 
  successful creation.
- FR-03 A Requester can view a paginated list of only their own Tickets in My Tickets.
- FR-04 A Requester can search their Tickets by Ticket Number or Summary text.
- FR-05 A Requester can filter their Tickets by Category, Requested Priority, and 
  Current Status.
- FR-06 A Requester can sort their Ticket list by Created Date, Last Updated, or 
  Ticket Number.
- FR-07 A Requester can open a Ticket Detail screen for a Ticket they own.
- FR-08 A Requester can add a permitted Attachment to an existing owned Ticket.
- FR-09 A Requester can soft-remove one of their own Attachments.
- FR-10 A Requester can download an active (non-removed) Attachment they own.
- FR-11 The system provides a Development Requester Selection screen to simulate 
  a logged-in identity for testing purposes.
- FR-12 A Requester can change their selected Development Requester identity at 
  any time via a "Change Requester" action.

## 5. Business Rules

### Ticket defaults & system-generated values
- BR-01 The official Ticket Number is generated by the backend and must be unique.
- BR-02 A new Ticket begins with Current Status "New".
- BR-03 Ticket Date is set automatically to the server time at creation and is read-only.

### Development Requester selection
- BR-04 Lab 2 uses a Development Requester selector instead of login. The selected 
  identity is for testing only and is not authentication.
- BR-05 Only active Development Requesters appear in the selector; inactive 
  Requesters are excluded.
- BR-06 The selected Requester is stored client-side (e.g. local state/session) and 
  is required before any ticket screens can be accessed.
- BR-07 Changing the selected Requester reloads all Requester-specific data (My 
  Tickets, Ticket Detail access) under the new identity.
- BR-08 If no active Development Requesters exist, the selector shows an empty 
  state and blocks entry into the ticketing screens.

### Ownership
- BR-09 A Ticket belongs to exactly one Requester (the one selected at creation time).
- BR-10 A Requester may only view, list, or modify Tickets and Attachments they own; 
  the backend must enforce this independent of the frontend.
- BR-11 Attempting to access another Requester's Ticket or Attachment returns a 
  safe not-found/forbidden response, not the actual data.

### Search, filtering, sorting, pagination
- BR-12 Search matches against Ticket Number and Summary, case-insensitive, partial match.
- BR-13 Filters (Category, Requested Priority, Current Status) can be combined; 
  results must satisfy all active filters simultaneously (AND logic).
- BR-14 Default sort is Created Date descending (newest first) unless the Requester 
  selects another sort field.
- BR-15 Page size is fixed or selectable within a documented range (e.g. 10 per page); 
  invalid page numbers return the nearest valid page or an empty result, not an error.

### Validation & duplicate-submission prevention
- BR-16 Ticket Summary is required, trimmed, and must be between 5 and 150 characters.
- BR-17 Ticket Description is required, trimmed, and must be between 10 and 2000 characters.
- BR-18 Category, Related System, and Requested Priority are required selections 
  from active, seeded values.
- BR-19 The Submit button is disabled while a request is in flight to prevent 
  duplicate ticket creation from repeated clicks.

### Failure behavior
- BR-20 If ticket creation fails after form submission, all entered field values 
  are preserved on screen so the Requester does not need to re-enter data.
- BR-21 If the backend or database is unavailable, the UI shows a clear, safe 
  error message without exposing internal error details.

### Attachment rules
- BR-22 Allowed attachment types are JPG, JPEG, PNG, WEBP, and PDF only.
- BR-23 Maximum attachment size is 5 MB per file.
- BR-24 A Ticket may have at most 5 active (non-removed) Attachments at any time.
- BR-25 Attachment removal is implemented as soft removal; the database record 
  is retained but flagged as removed, never hard-deleted.
- BR-26 A removed Attachment remains visible as metadata in the UI but cannot be 
  downloaded or previewed.
- BR-27 If a Ticket is created successfully but an attachment upload fails, the 
  Ticket itself remains valid and the Requester is shown which specific file(s) failed.
- BR-28 Only the owning Requester may add or remove Attachments on their own Ticket.

### Inactive Requesters
- BR-29 An inactive Development Requester cannot be selected and does not appear 
  in the selector dropdown, even if they own existing Tickets.

### Empty & no-results states
- BR-30 If a Requester has zero Tickets, My Tickets shows an "empty state" message 
  distinct from a "no results" message shown when filters/search return zero matches.

### Ticket Detail access
- BR-31 The Requester Ticket Detail screen displays Ticket header fields as 
  read-only; only Attachment actions (add/download/remove) are interactive.

### Transition to Lab 3
- BR-32 The Development Requester selector and its client-stored identity must be 
  clearly labeled as a temporary testing mechanism to be replaced by real 
  authentication in Lab 3, with no passwords, sessions, or tokens implemented now.

## 6. UI Specification Summary
See docs/lab-02/ui-spec.md for full detail. Summary: application shell with 
TokTickIT branding, My Tickets and Create Ticket navigation, and current 
Development Requester identity display. All screens follow the Zen Green theme 
(primary #006B3C, secondary #0B7A46, pale green #EAF6EF backgrounds for 
selected/success states). Editable fields have white backgrounds with neutral 
borders; read-only fields use soft gray-green shading. Every screen implements 
loading, empty, error, and success states, and is responsive at desktop (≥992px), 
tablet (768-991px), and mobile (<768px) breakpoints.

## 7. Data Changes
See prisma/schema.prisma for full detail. New models: RequesterUser (id, name, 
email, isActive, createdAt), RelatedSystem (id, name, isActive, createdAt), Ticket 
(id, ticketNumber, requesterId, categoryId, relatedSystemId, summary, description, 
requestedPriority, currentStatus, createdAt, updatedAt), Attachment (id, ticketId, 
fileName, storedName, fileType, fileSize, isRemoved, removedAt, removedReason, 
uploadedAt). Category model (from Lab 1) gains a reverse relation to Ticket. 
Indexes added on Ticket.requesterId, Ticket.currentStatus, and Attachment.ticketId 
to support ownership filtering and lookup performance.

## 8. API Contract
See docs/lab-02/api-spec.md for full detail. Summary of required endpoints:

- GET /api/categories — active Categories (reused from Lab 1)
- GET /api/related-systems — active Related Systems
- GET /api/requesters — active Development Requesters
- POST /api/tickets — create a Ticket for the selected Requester
- GET /api/tickets?requesterId=&search=&category=&priority=&status=&sort=&page= — 
  paginated, filtered, sorted list of the Requester's own Tickets
- GET /api/tickets/:id?requesterId= — retrieve one owned Ticket with its Attachments
- POST /api/tickets/:id/attachments — upload an Attachment to an owned Ticket
- GET /api/attachments/:id — retrieve Attachment metadata
- GET /api/attachments/:id/download — download an active Attachment
- PATCH /api/attachments/:id/remove — soft-remove an owned Attachment

All Ticket and Attachment endpoints validate ownership server-side using the 
requesterId supplied by the client, returning 403/404 rather than the actual data 
when ownership does not match.

## 9. Acceptance Criteria

- AC-01 Given valid Ticket data, when the Requester submits the form, then one 
  Ticket is saved and the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open 
  My Tickets, then the Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is 
  requested, then the Ticket data is not returned.
- AC-04 Given the Summary field is empty, when the Requester submits the form, 
  then a field-level validation message appears and the API is not called.
- AC-05 Given the Description field is empty, when the Requester submits the form, 
  then a field-level validation message appears and the API is not called.
- AC-06 Given a file larger than 5 MB is selected, when the Requester attempts to 
  attach it, then an error message is shown and the file is not uploaded.
- AC-07 Given a file of an unsupported type is selected, when the Requester 
  attempts to attach it, then an error message is shown and the file is not uploaded.
- AC-08 Given a Ticket already has 5 active Attachments, when the Requester 
  attempts to add a 6th, then the upload is rejected with a clear message.
- AC-09 Given the backend is unavailable, when the Requester submits the Create 
  Ticket form, then a safe error message is shown and all entered field values 
  remain in the form.
- AC-10 Given a Requester has zero Tickets, when they open My Tickets, then an 
  empty-state message is shown (not a no-results message).
- AC-11 Given a Requester has Tickets but applies filters matching none of them, 
  when they view My Tickets, then a no-results message is shown.
- AC-12 Given a search term matching an existing Ticket's Summary, when the 
  Requester searches, then only matching Tickets are shown.
- AC-13 Given more Tickets exist than fit on one page, when the Requester views 
  My Tickets, then pagination controls allow navigating to subsequent pages.
- AC-14 Given Requester A is selected and switches to Requester B, when My Tickets 
  reloads, then only Requester B's Tickets are shown.
- AC-15 Given an owned Ticket, when the Requester opens Ticket Detail, then all 
  header fields are displayed as read-only.
- AC-16 Given an owned Ticket with an active Attachment, when the Requester clicks 
  download, then the file downloads successfully.
- AC-17 Given an owned Ticket with an active Attachment, when the Requester 
  soft-removes it with a reason, then the Attachment shows as removed and cannot 
  be downloaded or previewed.
- AC-18 Given a Ticket belonging to another Requester, when the current Requester 
  attempts to access its Ticket Detail directly (e.g. via URL/ID), then access is 
  denied and no Ticket data is returned.
- AC-19 Given no active Development Requesters exist, when the Selection screen 
  loads, then an empty state is shown and ticket screens remain inaccessible.
- AC-20 Given the viewport is mobile-sized (<768px), when any Lab 2 screen is 
  viewed, then fields stack vertically with no horizontal scrolling or clipped 
  content.
